# Defect pass: callLater recovery, GTimer thread safety, idle event loop, test coverage

Follow-up to the risk register in `OPEN-RISKS-20260802.md`. Scope was "resolve the risks except
the ones related to GCoreApplication", so R1 (re-exec CPU spin), R6 (platform dispatchers) and R9
(singleton guarding) are deliberately untouched and remain open. R4 (the inert `parent` argument)
was already resolved by the owner in `bd19dbb`.

Verified on Windows/MSVC and WSL2/GCC+AddressSanitizer: **46 tests, both exit 0, no LeakSanitizer
output.** Four new tests; each fix that has runtime behaviour was confirmed to be caught by its
test by temporarily restoring the old code.

---

## R2 — `callLater()` no longer disables itself permanently after one failed dispatch

`scheduleCallLater()` inserts its key into the pending registry *before* attempting to dispatch.
If the target had no dispatcher, the queued metacall was destroyed but the registry entry was
left behind — and every later `callLater()` for that pair then matched the stale entry, took the
"already scheduled" branch, and never dispatched again. The pair stayed dead for the rest of the
object's life even after a dispatcher existed.

`dispatchMetaCall()` now returns `bool` (it is private, so the signature change costs nothing),
and `scheduleCallLater()` erases the entry when dispatch reports failure, so the next call
re-arms. The failed call itself is still lost — recovering it would need a retry queue with its
own ownership rules, which is a larger design question.

`GObjectDefectTest.CallLaterRecoversAfterFirstDispatchFails` covers it: call once with no
dispatcher (expected to be lost), move the target to a running worker, call again, and require
the second one to run. Reverting the erase makes it fail.

## R3 — `GTimer` now implements the thread safety it documents

All four members (`m_interval`, `m_timerId`, `m_singleShot`, `m_active`) were plain and unguarded
while every accessor's doxygen ended in "Thread-safe". Added `m_mutex` covering all of them.

Atomics alone would not have been enough: `start()` is a read-modify-write across several members,
so two concurrent calls could interleave and strand a registered timer. `start()`/`stop()` are now
atomic as a whole via private `startLocked()`/`stopLocked()` helpers.

The mutex is deliberately **not** held across `timeout.emit()` — a slot calling back into
`stop()`/`start()`/`isActive()` would otherwise self-deadlock on a non-recursive mutex, exactly
the failure fixed in `~GObject()` yesterday. `GTimerDefectTest.SingleShotIsStoppedBeforeTimeoutIsEmitted`
exercises that reentrancy, so a regression hangs rather than passing quietly.

## R7 — `GTimer::timerEvent()` stops before emitting

Was `timeout.emit(); if (m_singleShot) stop();`, so a slot observed `isActive() == true` on a
timer about to stop, and `GTimer` read `m_singleShot` and called `stop()` *after* arbitrary user
code had run. Now stops first and emits last, matching `QTimer::timerEvent()`.

**Residual hazard, documented at the call site:** `emit()` still executes inside the `GSignal`
member of the object itself, so deleting a timer outright from a directly connected timeout slot
remains unsupported. Use `deleteLater()`. The reordering removes our own post-user-code member
access; it cannot make destruction-during-emit safe.

## R8 — `GObject` copy/move explicitly deleted

These were already deleted implicitly by the `std::mutex` members, but only by accident. Stated
explicitly, because `m_life` is a `shared_ptr`: a copy would raise its use count so
`~GObject()`'s `m_life.reset()` would no longer expire the token, every `connect()`/`callLater()`
wrapper's `weakLife.lock()` would keep succeeding, and slots would be invoked on a destroyed
object. That is a use-after-free an unrelated refactor could reintroduce silently.

## R10 — idle event loops no longer wake ten times a second

`maxWait` was capped at 100 ms whether or not anything was scheduled. With no timers registered
the wait is now unbounded, so a fully idle thread costs nothing.

Making that safe required two supporting fixes, both real defects in their own right:

1. **`wakeUp()` never actually worked.** `processEvents()` waits on a predicate, so a bare
   `notify_all()` with no state change is a no-op — the waiter re-evaluated, saw nothing, and
   slept again. It only ever appeared to work because the 100 ms cap would have returned anyway.
   `wakeUp()` now sets a flag under `m_mutex` that the predicate tests, consumed once the wait
   returns.
2. **`interrupt()` had a lost-wakeup window.** It set its atomic without holding `m_mutex`, so it
   could land between a waiter evaluating the predicate as false and that waiter atomically
   releasing the lock to block — missing both the flag and the notification. Survivable with a
   100 ms cap; a permanent hang without one. It now takes `m_mutex` before setting the flag.

Covered by `IdleWaitBlocksButStillWakesOnPostedEvent` (must block while idle, must still wake on a
posted event) and `WakeUpEndsIdleWait`. Both call `interrupt()` on the failure path rather than
detaching, so a regression fails on its assertion in ~5 s instead of hanging the binary — the
first draft did hang, which is how that property got noticed.

## R5 — the three `GTimer` single-shot tests now assert something

`SingleShotStaticLambda`, `SingleShotStaticWithContext` and `SingleShotStaticWithReceiver`
declared a `fired` flag, slept, and never checked it. They were also almost certainly no-ops: they
ran on a main thread with no dispatcher, so `startTimer()` returned `-1` and the helper was
destroyed immediately. The static `singleShot()` family was effectively untested.

All three now run against a real worker event loop and assert the functor/member actually ran; the
context overload additionally asserts it ran *on the context object's thread*. The helper class's
counters were made atomic so the test thread can poll them without racing.

---

## Two things found while doing the above

**A pending `deleteLater()` leaks if the loop stops first** (now R13). Writing the R5 tests
produced real LeakSanitizer failures: the single-shot helper reclaims itself via `deleteLater()`,
and quitting the worker shortly after it fires drops that event. `~GEventDispatcherDefault()`
deletes pending events but cannot delete their receivers. The tests were restructured to drain the
loop before quitting — but the underlying behaviour is a library defect, not a test artifact, and
is trivially reachable by any `deleteLater()` closely followed by `quit()`.

**ThreadSanitizer, run for the first time, found a dispatcher use-after-free** (now R12, High).
All 46 tests pass under TSan while it reports 31 warnings. The dominant root cause: when a
`GThread`'s `run()` returns it deletes its own dispatcher, while other threads may be part-way
through `disp->registerTimer(...)` on a pointer they already loaded from `threadData()`. The
atomic protects the pointer, not the object's lifetime. TSan shows
`~GEventDispatcherDefault`/`~GEventDispatcherLinux`/`pthread_cond_destroy` racing against
`GObject::startTimer`, `registerTimer`, `GObject::event` and `GThread::exec`.

This is the same hazard the removed `GThread::setEventDispatcher()` had, reached through the
thread's own shutdown instead of an external swap — so yesterday's note that removing the setter
"resolves PS item 1 outright" holds only for the external-swap path.

Both were then fixed in the second pass below.

# Second pass: dispatcher lifetime (R12) and deferred-delete drain (R13)

Both fixes follow Qt's approach, after reading how `qtbase` handles the same two problems.

## R12 — the dispatcher now outlives in-flight use

**What Qt does.** Two things, and the second is the interesting one. `QObject::startTimer()` and
`killTimer()` simply *refuse* cross-thread calls (`"Timers cannot be started from another
thread"`), so the dangerous case never arises. And `QCoreApplication::postEvent()` does not queue
*through* the dispatcher at all — it appends to `QThreadData::postEventList`, which is refcounted
and mutex-protected, and only touches the dispatcher to call `wakeUp()`. The event queue outlives
the dispatcher because it does not live in it.

**What we did instead, and why.** Adopting Qt's thread-confinement rule would mean breaking a
documented promise — our `startTimer()`/`killTimer()` are documented thread-safe, and existing
tests exercise them across threads. Moving the queue out of the dispatcher into `GThreadData`
would be the fuller Qt-faithful change, but it is a large refactor of the most delicate file in
the project.

So we took the smaller change that makes the existing contract actually true: `GThreadData` holds
the dispatcher by `std::shared_ptr`, and `dispatcher()` hands back a **strong reference**. A
finishing thread drops its own reference rather than deleting the object, so anything mid-call
keeps it alive until done. `GThread::exec()` holds its reference across `processEvents()`,
`GThread::eventDispatcher()` returns a `shared_ptr`, and `GCoreApplication` holds its dispatcher
by `shared_ptr` instead of `unique_ptr` (a mechanical ownership change — not the deferred rework).
`GThreadData::ownsDispatcher` is gone entirely; shared ownership already encodes it.

**Verified:** the 3 vptr races (ctor/dtor vs virtual call) are gone, and the new
`GThreadDefectTest.DispatcherUseDuringThreadShutdownStress` — 40 trials of cross-thread
`startTimer()`/`killTimer()` racing a thread teardown — reports zero TSan warnings.

## R13 — deferred deletes are drained at thread shutdown

**What Qt does.** `QThreadPrivate::finish()` calls
`QCoreApplication::sendPostedEvents(nullptr, QEvent::DeferredDelete)` immediately after emitting
`finished()`, and *before* `cleanup()` destroys the dispatcher.

We mirror that exactly: `GAbstractEventDispatcher::processDeferredDeletes()` drains outstanding
deferred deletes, and `GThread`'s run lambda calls it after `run()` returns and before releasing
the dispatcher. It is public alongside `processEvents()`/`wakeUp()`/`interrupt()` because, like
them, it drives the loop as a whole and cannot be aimed at a specific receiver.

The implementation loops until no deferred deletes remain (destroying an object can queue more),
dispatches with `m_mutex` released (`~GObject()` calls `removeEventsForReceiver()`, which takes
the same non-recursive mutex), and tracks already-destroyed receivers so a double `deleteLater()`
cannot dispatch twice into freed memory — the same guard `processEvents()` uses.

**Still open:** `GCoreApplication::exec()` does not call it on the way out, so the main-thread half
of this leak remains. One line, deliberately left to the GCoreApplication rework.

## Also fixed: a data race in the test suite

`GObjectTest.CallLaterMultipleCycles` spun on a plain `bool sync1Done` written by a worker thread.
That is a real data race (and a loop a compiler may hoist), not a library problem — now
`std::atomic<bool>`. TSan warnings for that test: 1 → 0.

# Third pass: timers are thread-confined, matching Qt

**This corrects a mistake in the R3 fix earlier today.** `GObject::startTimer()`/`killTimer()`
carried doxygen saying "Thread-safe", so R3 treated that as a contract to honour and added a mutex
to `GTimer` to make it true. Qt does the opposite: `QObject::startTimer()` and `killTimer()`
*refuse* cross-thread calls outright —

```
QObject::startTimer: Timers cannot be started from another thread
QObject::killTimer: Timers cannot be stopped from another thread
```

— because the timer lives in the dispatcher owned by the object's thread, and only that thread's
loop can deliver the resulting `timerEvent()`. The comment promised something Qt does not offer,
and per the owner it was simply wrong. The library now matches Qt.

## What changed

- `GObject::startTimer()` and `killTimer()` reject calls from any thread other than the object's
  own: a warning on stderr and `-1` / no-op, mirroring Qt's text. Both doc comments now state the
  restriction instead of claiming thread safety. `startTimer()` also no longer consumes a timer id
  on the failure paths, and warns separately when the thread has no dispatcher at all — Qt has
  that same second diagnostic.
- `GTimer::start()`/`start(int)`/`stop()` inherit the restriction (they are plain forwards to
  `startTimer()`/`killTimer()`, exactly as `QTimer::start()`/`stop()` are) and now document it,
  including the `GObject::callLater(&timer, &GTimer::start, 50)` idiom for arming a timer that
  lives in another thread.
- `GTimer`'s mutex is **kept**, with a corrected comment. It no longer claims to make `start()`
  cross-thread callable; it is there because `timerEvent()` runs on the timer's own thread while
  the plain accessors may be read from another, and because `start()` is a read-modify-write that
  must not interleave with a reentrant `stop()` from its own timeout slot.
- `~GTimer()` no longer routes through `stop()`. Destroying a timer from another thread would
  otherwise emit a spurious warning for cleanup that happens anyway: `~GObject()` calls
  `removeEventsForReceiver()`, which strips the object's timer registrations from the dispatcher.
  This was caught by the new warning firing during the test run.
- **`GTimer::singleShot(msec, context, functor)` was silently broken by the new rule** and is
  fixed the way Qt fixes it. It used to `moveToThread(ctx->thread())` and then call `startTimer()`
  from the *calling* thread. Qt's `QSingleShotTimer::startTimerForReceiver()` arms directly only
  when the receiver is already on the current thread, and otherwise moves itself to the receiver's
  thread and posts an event to start the timer *there*. Ours now does the same, using
  `callLater()` as the hop, and the helper deletes itself if it cannot be armed.

## Ripple effects

- `GEventDispatcherDefaultDefectTest.NewShorterTimerWakesPromptly` armed two worker-affine timers
  from the main thread; both now go through `callLater()`.
- `GObjectDefectTest.ConcurrentMoveToThreadAndThreadDataAccessStress` and
  `GThreadDefectTest.DispatcherUseDuringThreadShutdownStress` hammered `startTimer()`/`killTimer()`
  cross-thread. That is no longer a supported operation, so both now hammer queued signal emission
  instead — which is the cross-thread dispatcher path that genuinely must stay safe, and is what
  the R12 stress test was really about.

## Verification

48 tests pass on Windows/MSVC and WSL2/GCC+ASan, both exit 0, no leaks, and **zero warnings
emitted during the run** — the suite no longer contains a cross-thread timer call. A standalone
probe confirms the guard fires and returns `-1` when a timer is started from the wrong thread.

ThreadSanitizer: **18 → 13** (11 data race, 2 double-lock). Several R14 reports disappeared with
this change, which supports the idea that they were tied to cross-thread `registerTimer()` racing
the dispatcher's timer-collection loop rather than being pure noise. The rest remain untriaged.

Running total for the day: **138 → 13**.

# Fourth pass: moveToThread confinement, timer migration, threadData made private

## moveToThread() is thread-confined

Same correction as the timers: the doxygen said "Thread-safe", Qt documents the opposite —
*"this function is not thread-safe; the current thread must be same as the current thread
affinity ... it can only 'push' an object from the current thread to another thread, it cannot
'pull' an object from any arbitrary thread"*. `GObject::moveToThread()` now enforces exactly that,
warns on refusal, and returns `bool` as Qt 6.11 does.

Qt's one exception is reproduced verbatim — *"objects with no thread affinity can be 'pulled' to
the current thread"* — and it turned out to be load-bearing rather than a nicety: without it,
`GThread::start()`'s own `this->moveToThread(this)` would be refused, since a GThread created on
the main thread has no affinity until its run loop adopts it.

## Active timers now move with the object

Qt: *"all active timers for the object will be reset. The timers are first stopped in the current
thread and restarted (with the same interval) in the targetThread."* We did not do this, so a
moved object's timers kept firing on the thread it had left — delivering `timerEvent()` where the
object no longer lived, which is exactly what the confinement rules exist to prevent.

Implemented the way Qt implements it. Qt sends itself a `QEvent::ThreadChange` before switching
affinity; `QObject::event()` takes the timers off the **old** dispatcher, unregisters them
(deliberately *not* returning the ids to the pool, so they stay valid), and queues a lambda via
`invokeMethod(..., Qt::QueuedConnection)` that re-registers those same ids on whatever dispatcher
the object has by the time it runs — which, the affinity having already changed, is the **new**
thread's. Qt uses its own queued-call machinery to satisfy its own thread-confinement rule.

Ours does the same with `dispatchMetaCall(..., G::QueuedConnection)`, backed by a new
`GAbstractEventDispatcher::takeTimersForReceiver()` (protected, friended to GObject like the other
receiver-targeting operations). Covered by
`GObjectDefectTest.MoveToThreadCarriesActiveTimersToTheNewThread`, verified to fail when the
migration is disabled.

## GTimer follows QTimer exactly

The mutex added earlier today is gone — `QTimer` has no locking of any kind, and every GTimer
member is only ever touched from the timer's own thread. All "Thread-safe" claims removed; the
class doc now states the constraint. `~GTimer()` calls `stop()` when active, matching
`QTimer::~QTimer()`, including Qt's wart that destroying an *active* timer from another thread
warns.

## threadData() is private

`GObject::threadData()` and `GThread::threadData()` are now private (the latter friending
`GObject`), matching Qt, where `QObjectPrivate::threadData` is not public API. This was the last
public handle onto the dispatcher plumbing — the route by which the R12 dispatcher hijack was
reachable before `GThreadData`'s members were encapsulated. Verified unreachable by compile probe,
with a positive control confirming the intended surface still builds.

## What the new warnings caught

Turning misuse into a visible diagnostic immediately found four instances of it in our own tests:
a timer destroyed from the wrong thread, cross-thread `setInterval()`/`setSingleShot()` (a real
data race once GTimer's mutex was removed), a stress test bouncing an object between threads from
two *other* threads, and worker-affine timers being armed from the main thread. All fixed; the
suite now runs with **zero warnings**.

## Verification

49 tests pass on Windows/MSVC and WSL2/GCC+ASan, both exit 0, no leaks, zero warnings.

ThreadSanitizer rose from 13 to 41, including a new `lock-order-inversion`. That was investigated
rather than accepted: the reported cycle contains an edge that **cannot occur** — TSan claims a
dispatcher mutex is held at `GThread.cpp:91`, where the only lock taken is `m_waitMutex` — and both
dispatcher mutexes in the cycle print with address `0x0`, meaning TSan no longer holds the objects
at all. It is a phantom cycle assembled from destroyed mutexes, filed as R16 with the analysis so
nobody re-derives it. The remaining count increase is the same unexplained R14 pattern, amplified
by the new tests' much heavier cross-thread posting; R14 itself is still open.
